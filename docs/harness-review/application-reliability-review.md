# Delta application reliability review

Source review on 2026-09-27 of Delta Mobile `83b2319` (1.0.79/code135) plus an uncommitted UI pass. The UI pass changes Settings, Agent, Connections, and the conversation shell, so its final behavior is not yet a stable commit. The installed wireless Pixel (`10.0.0.25:37197`) reports Delta 1.0.79/code135. These are source findings, not ARTEMIS acceptance or app speed measurements. See [the agent harness audit](agent-harness-audit.md) for the model/tool architecture and tool inventory.

## Findings to resolve before expanding the agent

| Priority | Source finding and user effect | Required correction and acceptance evidence |
| --- | --- | --- |
| P0 | AI Lab's no-key branch constructs a `DiagnosticReport` with `verdict: 'healthy'`, nominal subsystems and recommendations without running a diagnostic (`src/screens/ailab/AgentsSection.tsx:70-113`). Its Live controls send a fixed silent PCM string and a 1x1 test JPEG while telling the user microphone audio/camera frames were streamed (`:133-150`, `:195-214`). | Show unavailable/setup states when no key or capture source exists. Connect real media capture only after permissions and explicit user action; report actual send results. Confirm through ARTEMIS and inspect trace/log evidence. |
| P0 | The in-app MCP host creates an HTTP listener only under Node, but sets `status = 'running'` unconditionally (`src/core/mcp/mcpHostService.ts:83-131`). On React Native, the UI can advertise a reachable host with no listener. A Node bind failure is also logged then reported as running. | Add a supported Android listener or make host unavailable on Android. Make `running` contingent on a bound endpoint, then probe `/mcp` from the host through the intended forwarding route. |
| P1 | `McpStore.unregisterServerTools` deletes only name bookkeeping (`src/core/mcp/mcpStore.ts:205-211`). Disabling, removing, or failing a remote server does not remove its registered wrapper from `ToolRegistry`; later execution can still target a stale tool. | Add and exercise registry unregister/ownership, including resync name changes, disable, removal, failed discovery, and an in-flight call. Keep execution policy centralized. |
| P1 | Conversation mutations often ignore the durable-save result. `createSession`, `switchSession`, `renameSession`, `moveSession`, `deleteSession`, and `clear` return success or navigate after `await this.persist()` regardless of failure (`src/state/conversations/sessionStore.ts:318-375,491-566`). `ConversationHub` closes after creation or selection and ignores deletion's result (`src/features/conversations/components/ConversationHub.tsx:136-145,186-200`). | Make the result represent durable state, retain prior state on failure or clearly mark in-memory-only state, and keep the editor/navigation open with a retry. Verify restart after successful save and an injected write failure. |
| P1 | `saveDraft` ignores persistence failure and returns `void`; `useConversationDraft` writes the whole workspace on each keystroke, catches only thrown errors, and repeats writes on background/unmount (`sessionStore.ts:261-269`, `useConversationDraft.ts:21-56`). A failed save can be silent, while rapid typing can queue many disk writes. | Return/save a durable result, surface failure, coalesce writes without dropping the last revision, and measure typing latency plus restart recovery. Preserve the originating session for each draft. |
| P1 | `SessionStore.persist` snapshots `this.sessions/channels/activeSessionId` when its queued task executes, not when the mutation calls it (`sessionStore.ts:183-199`). A later mutation can change the data before an earlier queued write. `addTurnToSession` returns false on failure but leaves the new turn in memory (`:291-312`), which can confuse a retry. | Define an explicit queue/snapshot contract and commit or rollback consistently. Verify interleaved draft, send, edit, regenerate, switch, and failed-write cases without message duplication or reordering. |
| P1 | Legacy `Storage.saveJson` writes the native file directly and returns true without the checked path's backup/readback verification (`src/services/storage/jsonStorage.ts:163-193`). Prompt, memory, skill, and image stores still use it; memory-only fallback is also labeled success. In this installed Expo version, `File.write` is synchronous (`node_modules/expo-file-system/src/internal/NativeFileSystem.types.ts:208`), so a missing `await` is not itself a defect. | Migrate these stores to the checked `saveJsonResult` contract, preserve error provenance, and verify on-device read-after-write/restart and injected write failures. Do not describe memory-only storage as durable. |
| P1 | App Settings writes `geminiApiKey` to ordinary settings JSON (`src/core/settingsStore.ts:21,49,109`); SDK Live/cloud hooks use their separate stored key. The configured Live model is `gemini-3.8-flash-live-preview` (`:51`), while current official model documentation names a different Live model. | Establish one secure credential path and one supported model selection, then connect with a real key and record failure details. Do not infer success from a saved Settings field. Confirm the model against [Google's current list](https://ai.google.dev/gemini-api/docs/models) at implementation time. |
| P2 | The ordinary chat agent is a one-pass keyword dispatcher (`src/core/deltaAgent.ts`); Laya is called only for ambiguous flashlight intent (`:219-235`). Registry membership does not mean a tool is routable. Cloud and Live use separate registries/policy paths. | Build a bounded coordinator and one catalog only after the P0/P1 truth and persistence defects are fixed. Use capability/permission checks and confirmation at execution time. [The harness chapter](agent-harness-audit.md) records the proposed design, which awaits user feedback. |

The P0/P1 labels express review priority, not proof of exploit or a completed device failure. Source alone is sufficient to show the unconditional status, fabricated report, missing unregister, and ignored returns. Phone acceptance must still reproduce the user-facing outcomes. Other source claims in the harness chapter, including fabricated `doctor`/`device_info` results and `clear_history`/`hand_off` semantics, remain open and were not changed here.

## Exploration and BDD gate

The next device pass should first establish app/native/JS identity, then use ARTEMIS to observe exact labels, waits, transitions and failure states. In order: (1) send/edit/regenerate/restart with stable turn IDs and ordering; (2) forced persistence failure and retry, including drafts; (3) Laya missing/download/load/preview/offline behavior; (4) Android STT to Nano to Kokoro with real playback start and completion; (5) MCP disabled/remove/reconnect and host reachability; (6) real cloud/Live setup and consented tool calls. Record serial, repeats, successes/failures, monotonic stage timings and trace/artifact IDs. Author runnable BDD only from verified UI paths, using dynamic locators and verified coordinate fallbacks per the repository's ARTEMIS rule. Existing unit-test failures can be investigated independently, but no new mobile test code is authorized before that exploration.
