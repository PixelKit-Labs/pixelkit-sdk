# Delta agent harness: source audit and design checkpoint

Source audit on 2026-09-26. Delta Mobile HEAD was `83b2319` (1.0.79/code135), with unrelated local edits present. PixelKit SDK HEAD was `8595882` (1.6.45). This chapter describes source behavior, not a phone benchmark or acceptance of Laya, Kokoro, Live, or MCP. The proposed design below needs user review.

## Current execution paths

| Entry | Implemented path | Boundary and evidence gap |
| --- | --- | --- |
| Typed or recognized Nano turn | `ConsoleScreen.processPromptWithNano` calls `DeltaAgent.processUserTurn`, persists the user turn, then calls `useGeminiNano.sendMessage`. `DeltaAgent` scans text with keyword rules, executes every matched action sequentially through `ToolRegistry`, retrieves one memory match, and prefixes results/telemetry to Nano's text prompt. | This is a one-pass dispatcher, not a model/tool/result loop. Nano's streaming output is a reply, not a validated tool call. `ConsoleScreen` writes pre-generation `modelMs: 0`; routing can already include Laya inference. |
| Gemini Nano | The published `@pixelkit-labs/sdk/mlkit` hook uses ML Kit GenAI Prompt API/AICore through `PixelNano`, resending bounded recent message history and recording native latency/first-token/decode metrics. | No cloud fallback or structured tool calling in this chat path. The hook records its own history separately from `SessionStore`. The app consumes SDK 1.6.39, not the unreleased SDK trace correction. |
| Laya | `localTorchIntent` resolves explicit flashlight commands; only an ambiguous flashlight request may call `layaService.disambiguateTorch` when opted in. A candidate shapes a clarification and never authorizes execution. The local ONNX model is queued and lazily loaded on CPU. | General tool/MCP routing, arguments, calibrated thresholds, and phone-verified inference are absent. The 15-second caller deadline can expire while native work continues. Model download and ready-state flows still need ARTEMIS acceptance. |
| Speech and Kokoro | `useSpeechAI` uses Android recognition for Nano text input. `ConsoleScreen.speakReply` passes Kokoro's installed TTS package to SDK `useSpeech`; the SDK binds Android's external Sherpa-ONNX TTS service. | Kokoro is not bundled inference in Delta. Playback completion and service binding were previously observed; audible identity and request-to-playback-start latency remain unverified. Manual replay/follow-up and wake reliability remain separate tests. |
| Gemini Live chat | `ConsoleScreen` calls SDK `useGeminiLive.connect/sendText` directly; the visible Live transcript comes from that hook. Its WebSocket path uses the SDK's separate global hardware registry and calls `runTool` when the model requests functions. | It bypasses `DeltaAgent`, Laya, the Delta tool registry/confirmation gate, and normal `SessionStore` turn persistence. The chat UI does not wire the SDK's audio/video send methods to a microphone/camera stream. Live audio is generated by Live, not Kokoro. |
| Cloud agent and diagnostic team | AI Lab alone mounts `useCloudHardwareAgent`, whose SDK loop calls Gemini `generateContent`, executes function calls, and stops after a step budget. AI Lab also exposes the SDK diagnostic team. | Neither is the normal chat harness. The app never calls SDK `registerHardwareTools`, so this source does not establish usable hardware functions in the SDK's separate global registry. The AI Lab's no-key diagnostic branch fabricates a healthy report and specialist observations without reading those subsystems. Remove this branch, not merely its label. |
| Remote MCP and local host | `McpStore` discovers remote tools and registers namespaced wrappers in Delta's registry. Two example remote servers default disabled. `McpHostService` declares 16 Pixel tools and has a Node `http` listener. | There is no evidence of a connected remote server by default. `unregisterServerTools` only drops its name bookkeeping, leaving stale callable entries. The host marks itself `running` even when no Node listener exists; no React Native HTTP listener appears in this source. MCP keyword routing passes `{}` rather than extracted/validated arguments. |

SDK Live's current app preference is `gemini-3.8-flash-live-preview`, while the current Google model list names `gemini-3.8-live` ([Google model list](https://ai.google.dev/gemini-api/docs/models)). The SDK default is the older `models/gemini-2.0-flash-exp`; the app overrides it. A saved `SettingsStore.geminiApiKey` is generic JSON, but SDK Live and cloud agent read `getStoredApiKey()` from their own SecureStore key or an environment variable. Saving the app setting alone therefore does not supply those SDK hooks. Live sends a long-lived API key in a WebSocket URL; Google's [ephemeral-token guidance](https://ai.google.dev/gemini-api/docs/live-api/ephemeral-tokens) recommends short-lived tokens for direct mobile clients. These are source/protocol findings, not a successful or failed Live connection test.

## Tool inventory and what it means

The Delta `ToolRegistry` constructor registers **49 definitions** across these groups. Registration means a schema and executor are present; it does not prove a capability is available on this device, routed from chat, permissioned correctly, or device-verified.

The in-app MCP host separately declares 16 `pixel_*` tools. Those are server exports, not 16 additional chat-registry tools. Remote MCP tools would be additional only after discovery; the two built-in example servers are disabled. Agent → Tools displays definitions and schemas, not enable switches or live availability.

Several claims need immediate correction before expanding the catalog. `diagnostics_summary` substitutes `nominal` for absent thermal status and `doctor` calls a set of available hook fields “verified active”; `device_info` hardcodes Pixel/silicon/security/display defaults on unavailable reads. `clear_history` reports `cleared: true` inside its executor but does not itself clear `SessionStore`; the chat presenter performs the actual clear in its special confirmation path. `hand_off` changes `RosterStore.activeAgentId`, but neither `DeltaAgent` nor `ToolRegistry` consumes the roster's `toolScope` or `systemPromptModifier`. `show_card` and `use_skill` provide data/guidance, but the one-pass harness has no continuation that follows a skill or asks a model to populate card arguments. Tool parameters are descriptive in Delta's registry; there is no central runtime schema validator before executors. The SDK Live/cloud registry validates arguments but uses a different executor and does not pass through Delta's confirmation gate.

## Proposed target, pending user feedback

One turn coordinator should own input, provider choice, cancellation, persistence, tool policy and trace IDs. Voice, text and Live are input/output adapters to that coordinator. Keep explicit command rules for clear actions; let Laya propose typed candidate intents only when useful and available; let Nano answer or propose structured next steps within its real capability. Cloud use should be a separate, visible consented route, never an implicit Laya/Nano failure fallback.

Create one tool catalog with adapters for built-in tools, SDK hardware hooks and remote MCP. Each entry needs a machine-checked input/output schema, availability probe, provenance, effect/risk class, permission requirement, confirmation policy, timeout and cancellation behavior. Execution must revalidate arguments and device capability after any model proposal. A tool result must state observed effect or failure; model prose is never proof of action. Remove disconnected MCP entries and fail a hosted MCP start when no listener binds.

Implement a bounded loop: classify/request → select permitted candidate → validate arguments → confirm where needed → execute → observe result → decide whether another step is necessary → respond and persist. Carry `turnId`, `toolCallId`, `provider`, and `sessionId` through every stage; include limits on steps, wall time, retries and network use. A specialist agent should be a scoped worker in that same loop, with enforced tool permissions, a task/result contract and one accountable chief response. A roster label alone is not an agent.

Keep two voice experiences explicit: local cascade (Android STT → harness/Nano → Kokoro or phone TTS) and cloud duplex (Live audio). Live's tool calls must enter the same catalog/policy and its transcript must persist with provider provenance. Do not present Live as Kokoro speech. Record cold and warm request-to-first-output, recognition-final-to-submit, model first token/completion, tool effect confirmation, TTS playback start/completion, and UI persistence separately. Include failures and timeout counts; no end-to-end speed claim exists yet.

Recommended sequence: (1) remove fabricated healthy/device-success responses and correct visible capability states; (2) fix credential ownership and supported Live model/config, then verify a real connection; (3) unify tool execution/policy and MCP lifecycle; (4) add a small bounded loop with a few verified tools; (5) enforce specialist scopes only after the single-agent loop is reliable; (6) measure the local cascade and Live separately before optimizing. This is a proposed order, not an accepted product decision.

## Evidence, open questions and decision log

The latest prior phone check only established that Delta 1.0.79/code135 rendered chat on the authorized wireless Pixel after Metro recovery. It did not execute the flows audited here. No new BDD or performance data was authored in this source audit; ARTEMIS-led exploration remains required before mobile tests.

Open questions for the user: should an incomplete local request ask before cloud use, stay local, or use a previously approved automatic cloud policy? Should specialists collaborate within one foreground turn, run as background agents, or both? Which first three real jobs should define acceptance for the new loop? None is decided by this chapter.

Glossary: **candidate** is an untrusted suggested intent; **tool catalog** is the single schema/capability/policy inventory; **tool result** is an observed execution outcome; **turn coordinator** owns one user's complete request; **specialist** is a scoped worker with enforced permissions; **local cascade** is STT, local reasoning and external Android TTS; **Live duplex** is cloud audio streaming.

2026-09-26 decision log: record the current three-registry split and remove fabricated-success behavior as the first design priority. The unified coordinator, general Laya routing, provider escalation and specialist execution are proposals pending user feedback. This audit changes no SDK hook, native module, app behavior, or device acceptance status. Existing UI and Laya chapters remain historically accurate at their recorded source versions; diagrams and unrelated hardware glossary entries require no change.
